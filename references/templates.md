# 场景追踪与反例参考

按规模取用；不要求每项都建文件。证据采用已有测试、日志、文件、页面或回执，记录实际输出，而不是只写“PASS”。

## 一张场景表

开工从原话提取可独立验收的承诺，编号并关联必需场景。一个承诺可对应多个来源或分支。一次运行可为多项承诺提供证据，复用记录并标出各自依据。执行前写预期，执行后填实际、证据和结论。补充场景时保留原失败和范围变更。收尾从原话反查每项承诺是否有场景、关键证据和判定。

| 原始承诺编号 → 场景编号 | 原始入口 → 结果及必需条件 | 正例与关键反例的预期 | 实际观察与各关键环节证据 | 结论、影响及剩余动作 |
|---|---|---|---|---|
| R1 → S1：用户原话中本行核验的承诺 | 来源、触发、前置条件、结果对象、位置及时限 | 正例与反例各自应发生和不得发生的结果 | 正例和反例分别记录实例标识，标明各关键环节的证据位置、观察与替身范围 | 已验证、失败或未验证，说明适用范围及剩余动作 |

复杂场景可在证据格链接以下简短记录，避免把整张表撑宽：

```text
原始承诺编号、原话与场景编号：
本次验收条件／明确要求的机制：
输入：来源、样本或事件 ID；触发与前置设置
路径与证据：逐项列出关键环节、实际观察及本次实例的证据位置
方法：在哪个环境，用了什么真实组件和替身
预期：应发生什么；反例下不得发生什么
实际：观察到什么；对应版本、必要标识与证据位置
结论：已验证／失败／未验证；可支持的声明
缺口：影响、缺失条件、仍可做的工作、最小补证动作
```

纯函数或小修改只需“结果条件 → 直接检查 → 相关边界例 → 结论”，无需复制整张表。

## 从承诺选择反例

| 可能失真的成功判断 | 有价值的反例 | 要观察的事实 |
|---|---|---|
| 入口后面的测试绿，所以真实触发已接通 | 从约定的真实来源发起并保留接收记录；只有绑定检查时，触发保持未验证 | 是否从原始入口进入；手工注入没有覆盖哪段 |
| 找到了某个旧任务，所以关联正确 | 两个对象同名、同主题或同时间 | 正确对象获输入；歧义暴露；错误对象无副作用 |
| 收到 ACK，所以工作完成 | ACK 后执行失败或接收端不可用 | 失败/未知真实可见，完成状态未被误写 |
| 重试成功，所以恢复可靠 | 完成动作后丢回执，再重放同一请求 | 实际动作次数、对象与结果；不因未知盲目重做 |
| 功能存在，所以会自动运行 | 默认关闭、未订阅来源、进程退出 | 用户约定的默认行为是否成立；后台承诺覆盖什么环境 |
| 声称“AI 判断”就有模型监督 | 运行正常但任务报告偏离原目标；换一份未预写答案的材料 | 真实模型调用及依据；固定响应只证明协议，不能证明判断 |
| 正例成功，所以权限边界有效 | 过期身份、另一账户、授权已撤销 | 原动作未发生，拒绝原因和事实正确 |

只选会影响本次承诺的项；不为文案修改强加幂等、权限、进程树或生产故障实验。

## 三个迁移例子

### 事件型 Agent

承诺：“供应商回信后自动找到采购事项、更新比较表并向我汇报。”

把真实来信自动触发、关联正确事项、更新比较表、回报送达分别记为可判定的承诺。用同一封信的记录核对接收、关联、写入和送达，分别挂证据。若回报已送达却写错事项，送达可通过，归属失败，整体未完成。反例可用同主题不同供应商、重复投递或未授权的新动作。

手工调用 `receive(text)` 只能证明它之后的路径。通过受控邮件/模型夹具可验证适配协议，但不能补签真实订阅或语义判断。若现有部署没有该入口，应给出明确缺口，不能悄悄把承诺改为“用户复制邮件后回复”。

### 普通业务功能

承诺：“从订单页导出筛选后的 CSV，金额与原订单一致。”

追踪筛选参数、导出请求、文件内容与页面下载；反例优先选筛选条件丢失、金额精度或空结果，而不是测试不相关的后台 Agent 生命周期。使用已授权测试数据即可，不强制生产订单或商业收益证明。

### 小工具或资料交付

承诺：“现有文件名函数也接受大写 `.CSV`。”只需真实函数的大小写正例及相邻不支持扩展名反例，沿受影响调用者判断回归面。

若任务是资料比较，路径可为“用户指定来源 → 提取事实 → 比较准则 → 结论与引用”。反例是来源互相矛盾、证据缺失或例外条件；无需臆造一个后端运行验收。

## 交付表达

```text
本次交付：[按原定范围写实际成果与层级]

已验证：[逐项场景，证据链接，适用环境与方法]
关键反例：[输入/故障条件 → 实际行为 → 是否符合原预期]
仍有缺口：[未验证或失败的必需项、影响、最小补证或修复动作]
结论：[可以支持的完成声明；不能支持的扩展声明]
```

测试数量可以附带报告；场景覆盖、证据边界和必需项缺口决定结论。

## 核验细目

仅取用当前场景涉及的段落。

### 自动触发与外部状态

核对能力存在、默认配置、实际启用、部署与运行中哪些是原承诺所需。订阅、按钮、调度器、外部回调须有真实来源事件及对应接收记录；手工调用下游函数不覆盖这些入口。

接收、排队、开始、执行、发送、对方已读、业务验收分别判断，足够状态由原承诺决定。负向结果还须证明事件确实到达被检验环节；例如定时器未启动时，没有通知不证明过滤有效。观察窗口依据原时限和系统延迟确定，记录起止与观测方式。

### 模型判断

核对真实模型路径、输入上下文、输出及其参与决策的记录。固定响应可验证接线，判断质量须用未预写答案的代表性材料及独立事实或评分标准检验。模型自称已做某动作，仍需对应执行及目标端证据。

### 重试、恢复与证据

按原承诺选重复、超时、错对象、权限撤销、默认关闭等反例。动作完成却丢回执时，检查实际动作次数和目标状态，不能因结果未知就盲目重做。执行前确定观察期限与重试条件，环境故障归因须有证据。

静态源码、单元测试、回放、真实组件集成、现场运行和业务结果证明不同对象，不机械评级。没有现成标识时使用可复查的有界记录，不新建通用日志平台。实施中优先将低成本稳定复现的关键违约固化为现有回归断言；只读评审提供复现条件即可。
